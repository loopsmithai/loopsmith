# Loopsmith Kit — Feature Set

70 features, organized by journey in lifecycle order. The kit comes into being before it is used: the Loopsmith developer trains Smith and bootstraps the catalogue, family and package authors grow what's available, and the end user stands up and runs their own setup.

Some features describe packaging and dependency-resolution behaviors that may be fulfilled by existing infrastructure rather than built from scratch. They are included because they are user-observable — from the user's perspective they are Loopsmith features regardless of what fulfills them.

## Personas

A persona is a *kind of human*, not a hat: if two roles can genuinely be performed by two different people, they are two personas. The primary target is the **End User** — Loopsmith exists first to be its author's own Jarvis.

| # | Persona | Who they are | Analogue |
|---|---------|-------------|----------|
| **P1** | **Loopsmith Developer** | Smith's maker and maintainer. Builds the kernel, contracts, and grammar; trains Smith through apprenticeship; bootstraps the first catalogue. | rpm-ostree / Silverblue tooling devs |
| **P2** | **Family Author** | Uses a trained Smith to build families and blueprints — the curated substrate for a domain. | Fedora / Silverblue compose maintainers |
| **P3** | **Package Author** | Authors the individual packages the catalogue is built from — packages that provide a capability, reusable templates, and definitions of new capability types with their contracts. | rpm package maintainers |
| **P4** | **End User** | Stands up, wires, runs, and evolves their own setup, then lives in it. The primary target and the bulk of the feature set. | the person the system is built for |

## Bootstrap — The Apprenticeship (4 features)

The developer builds the kit and trains Smith. Before any catalogue, family, or blueprint exists, the developer runs Smith against real systems. Smith ships credentialed on structure (it knows the contracts, grammar, kernel — its "medical degree") but apprenticing on craft (agentic best practices — what makes a good setup for a real team). The developer is the attending; Smith is the resident. Each run teaches Smith more, and the output of the runs IS the catalogue.

| ID | Feature | User Story |
|---|---|---|
| BST-01 | Smith MUST ship credentialed on the kit's structural model — the kernel nouns, capability contracts, package grammar — as built-in knowledge, not learned. This is the irreducible seed: the structural knowledge that makes Smith a conforming builder from day one. | *As a **family author** using Smith for the first time, I want Smith to already understand the kit's structural model — the contracts, grammar, and kernel — so that I'm teaching it about my domain, not about the kit itself, and it verifies and authors reliably and efficiently from the very first run.* |
| BST-02 | Smith MUST be runnable against a real system with an empty catalogue — producing families, blueprints, templates, and packages from scratch through a supervised packaging run with the developer. The output of the run IS the first catalogue content. | • *As a **family author**, when I run Smith against a real system with an empty catalogue, I want Smith and me to co-author the first family, the first blueprint, and the first templates — producing real catalogue content, not stubs — so that the catalogue starts with battle-tested packages.*<br>• *As a **family author**, when I build a second family after the first, I want Smith to reuse what the first run produced and author only the delta, so that the abstraction proves itself — if the difference between two real setups collapses to a few packages, the model works.* |
| BST-03 | Smith's craft knowledge — what makes a good loop definition, how to structure a team's loops, when to split vs merge contexts — MUST grow through supervised practice with the developer, crystallized into skill packages. The developer guides, Smith proposes, the developer validates. | • *As the **Loopsmith developer**, when Smith proposes a craft choice that I know from experience won't serve the team well, I want to correct it and have that correction crystallized into a skill so that it gives better advice next time — not just to me, but to every future operator.*<br>• *As the **Loopsmith developer**, when Smith makes a good craft judgment unprompted, I want to validate it and capture it as a skill so that it becomes part of its repertoire, not a one-off.* |
| BST-04 | At the end of bootstrap, Smith MUST be re-packaged as a conforming agent template in its own catalogue — the bootstrap completes when Smith becomes a package that a blueprint ships, so that at n-0 the same Smith onboards end users. | *As an **end user**, when I install a blueprint that ships Smith, I want it included and ready out of the box — credentialed and craft-trained, packaged as a conforming agent template — so that I get a capable consultant from day one, not a blank agent I have to teach from scratch.* |

## Family Authoring — Growing the Kit's Reach (4 features)

The family author uses a trained Smith to build new families and blueprints for their domain. Could be the Loopsmith developer extending the kit, or a power user building families for their organization. Smith knows the craft but is learning about THIS author's specific domain. (Analogue: a Fedora/Silverblue compose maintainer — distinct from both the tooling developer above and the individual package maintainer below.)

| ID | Feature | User Story |
|---|---|---|
| PKG-10 | A family author MUST be able to use Smith to build a new family — a curated substrate package-set for a domain the kit doesn't yet serve — through a co-design process where Smith brings structural and craft knowledge and the author brings domain expertise. | *As a **family author**, when I work in a domain the kit has no family for — Smith carries the structural and packaging craft but none of that domain's knowledge — I want to co-author a new family with it, supplying the domain expertise myself, so that the kit gains a structurally sound substrate for the domain instead of an ad-hoc bag of configs.* |
| PKG-11 | A family author MUST be able to build a new blueprint on an existing family — adding the specific loop templates, actor configurations, and capability-providing packages that define a starting point for a use case within that domain. | • *As a **family author**, when a family already provides the substrate but has no blueprint for the role or use case I need to support, I want to author a new blueprint on it — selecting the loop templates, actor configurations, and capability-providing packages that define that starting point — so that someone can install one blueprint and get a working setup.*<br>• *As a **family author**, when I author a second blueprint on the same family, I want to reuse the shared substrate and write only the delta so that the family proves its value as a foundation.* |
| PKG-12 | Packages authored during family authoring MUST be publishable to a catalogue — with the author's consent — for reuse by other family authors and end users. | • *As a **family author**, when Smith and I author a package while building a family or blueprint, I want to be able to publish it to a catalogue so that another author can reuse it instead of re-authoring it.*<br>• *As a **family author** building for my organization only, I want to publish my packages to a private catalogue rather than a public one so that proprietary configurations stay internal.* |
| PKG-13 | Friction encountered during family authoring MUST feed back into the kit — when a family author hits a structural limitation (a contract too narrow, a missing capability type, a grammar gap), that friction MUST be surfaceable to the Loopsmith developer as a contribution. | • *As a **family author**, when I hit a structural limitation while building — a contract too narrow for my domain, a missing capability type, a grammar gap — I want that friction recorded and surfaceable to the Loopsmith developer so that the kit can evolve to support my domain.*<br>• *As the **Loopsmith developer**, when family authors across multiple domains hit the same contract limitation, I want to see the aggregated friction so that I know where the kit's model needs to grow.* |

## Packages (9 features)

The package author builds the individual units the catalogue is made of — declaring what each package provides and requires, giving capabilities stable identities, satisfying conformance contracts, and authoring reusable templates designed for independent composition. (Analogue: an rpm package maintainer.)

| ID | Feature | User Story |
|---|---|---|
| PKG-01 | A package MUST declare the capabilities it provides. | *As a **package author**, when I create a package, I want to declare what capabilities it provides so that the system can match it to setups that need those capabilities.* |
| PKG-02 | A package MUST declare the capabilities it requires, optionally constraining the acceptable version(s) of a required capability. | *As a **package author**, when my package depends on other capabilities to function, I want to declare those requirements — and pin version ranges where compatibility matters — so that the system ensures they're satisfied at the right versions before installation.* |
| PKG-03 | A capability MUST have a unique identity that packages reference in their provides and requires declarations. | *As a **package author**, when I declare a dependency on a capability, I want to reference it by a stable unique name so that the system resolves it unambiguously.* |
| PKG-04 | The kit MUST define a conformance contract per capability type, specifying the required configuration, required data relationships, and required observable behavior that a provider must satisfy. | *As a **package author**, when I build a package that provides a capability, I want a published contract that tells me exactly what my package must satisfy so that I know when I'm done.* |
| PKG-05 | A reusable actor and the loop template it runs MUST be independently composable — the same loop template runnable by different actors, and an actor able to run different loop templates. | *As a **package author**, when I create a loop template, I want any actor to run it; when I create an actor template, I want it assignable to any loop template — so that I don't create a template for every combination.* |
| PKG-06 | A package MAY declare the coding agent(s) it supports — zero (agnostic), one, or several. | *As a **package author**, when my package's content runs on some coding agents but not others, I want to declare exactly which it supports so that the system places it only where it can actually run.* |
| PKG-07 | A package MAY carry behavior the system runs at defined lifecycle points — at install/wire time (one-time setup: scaffolding, connecting to a source), at verification time, and at uninstall/removal time (cleanup: disconnecting sources, removing scaffolding) — not only static content. | *As a **package author**, when my package needs to do setup beyond dropping files and undo it cleanly on removal, I want to attach behavior that runs at install, verify, and uninstall so that installing wires it up and removing leaves no orphaned state.* |
| PKG-08 | A package MUST be able to ship a **meta-skill** — knowledge for working with the package, applied mainly at install, uninstall, troubleshooting, and runtime. The meta-skill is organized into sections — one for each of these, plus arbitrary author-defined sections — so the author can capture whatever is needed to handle the package well. | *As a **package author**, I want to be able to ship a meta-skill with my package — covering install, uninstall, troubleshooting, runtime, and any sections of my own — so that my package is handled competently across its lifecycle instead of by guesswork.* |
| PKG-09 | An agent MUST be able to apply a package's meta-skill — at install, uninstall, troubleshooting, and runtime — to make the judgment-based decisions the deterministic lifecycle hooks cannot, so that a package is correctly configured, kept working, recovered when it misbehaves, and cleanly removed, not merely installed. | *As a **user**, when a package needs judgment to set up, operate, recover, or remove — beyond what its deterministic hooks do — I want an agent to apply the package's meta-skill at the right moment so that it ends up correctly configured and working, not just dropped in or left broken.* |

## Discover & Choose (5 features)

*The user wants to understand what's available and pick a starting point.*

| ID | Feature | User Story |
|---|---|---|
| PKG-14 | A user MUST be able to browse available blueprints — curated starting points that combine a family's packages for a use case — and their descriptions before committing to one. | *As a **first-time user**, when I'm choosing a starting point, I want to see a list of available blueprints with descriptions of what each includes so that I can make an informed choice rather than assembling from scratch.* |
| PKG-15 | A user MUST be able to browse and search available packages by capability, and inspect a package's declared capabilities and conformance contracts before installation. | *As a **user**, when I need a specific capability, I want to search by what it provides and see every matching package with its requirements and contract summary so that I can make an informed choice before installing.* |
| PKG-16 | A capability MUST be declarable at multiple levels of specificity — a requirement for a general capability (e.g. work-tracker) MUST be satisfiable by any provider of a more specific variant (e.g. github-projects-tracker). | *As a **user**, when I require a general capability in my setup, I want any package that provides a more specific variant of it to satisfy that requirement so that I don't have to know the exact provider name up front.* |
| PKG-17 | When several providers exist for a capability the user is choosing, the system MUST offer the alternatives with their descriptions to select among. The system MUST NOT install anything silently: before assembly the user MUST see and approve the complete resulting set of packages, but MUST NOT be required to select every transitive dependency individually. | *As a **user**, when I pick a high-level option (say, an assistant), I don't want to be quizzed on every dependency it pulls in — I want to make the real choices, then see the full list of what will be installed and approve it, the way a package manager shows a transaction and asks y/n.* |
| PKG-18 | When a required capability has no available provider, the system MUST surface the unresolved capability to the user. | *As a **user**, when I try to stand up a setup and a needed capability has no provider in the catalogue, I want the system to tell me which capability is missing so that I know exactly what needs to be authored or sourced.* |

## The Consultation — Conversational Discovery with Smith (5 features)

*Smith acts as a consultant — not a form to fill out, but a back-and-forth conversation where Smith learns about the user's world, proposes architecture, explains trade-offs, and adapts to feedback. This is the n-0 product experience.*

| ID | Feature | User Story |
|---|---|---|
| PKG-19 | The builder agent MUST conduct discovery as a conversation — asking questions about the user's context, team, tools, and goals — not as a one-shot intake form. The agent MUST adapt its questions based on prior answers. | • *As a **user**, when I engage Smith for discovery, I want the questions to adapt to my previous answers rather than follow a fixed intake form so that Smith comes to understand my actual world instead of filling in a template.*<br>• *As a **user**, when I give an answer that doesn't fit Smith's expected flow, I want it to follow and explore it rather than force me back onto a predefined path.* |
| PKG-20 | When recommending a setup, the builder agent MUST explain why it recommends each component — what trade-off it represents, what alternatives exist, and what the user would gain or lose by choosing differently. | • *As a **user**, when Smith recommends a component, I want it to explain why — the trade-off it represents, the alternatives, and what I'd gain or lose by choosing differently — so that I make an informed choice, not a blind one.*<br>• *As a **user**, when Smith proposes a capability I didn't ask for, I want the rationale behind it so that I can accept or decline based on understanding, not authority.* |
| PKG-21 | The user MUST be able to redirect, reject, or refine any of the builder agent's proposals at any point in the consultation — and the agent MUST adjust its downstream recommendations accordingly, not just override or ignore the feedback. | • *As a **user**, when I tell Smith a recommendation is more than I need, I want it to scale back the whole recommendation — dropping that capability and anything that depended on it — so that I don't get a bloated setup.*<br>• *As a **user**, when I change my mind mid-consultation about a choice, I want Smith to re-evaluate everything downstream of it so that the recommendation stays coherent.* |
| PKG-22 | The builder agent MUST present choices — not just recommendations — when the user's needs can be met by meaningfully different architectures, and MUST help the user understand the implications of each path before proceeding. | *As a **user**, when my needs could be met by meaningfully different architectures, I want Smith to present each option with its concrete trade-offs so that I choose the architecture, not have it chosen for me.* |
| PKG-23 | The consultation MUST produce a shared, explicit understanding of what will be built — a summary the user reviews and approves before the builder agent begins authoring or assembling. | *As a **user**, before Smith starts building anything, I want to see a summary of what we agreed on — which capabilities, which packages, which sources will be wired, what's being authored from scratch — and explicitly approve it so that there are no surprises.* |

## Build a Setup with the Builder Agent (9 features)

*The user works with the builder agent (Smith) to go from an idea or existing setup to a running, verified configuration.*

| ID | Feature | User Story |
|---|---|---|
| PKG-24 | The builder agent MUST accept a target — a natural-language description of a desired setup, or a reference to an existing setup to replicate or extend — and determine the capabilities it requires, eliciting and refining the user's needs rather than only transcribing what exists. | • *As a **first-time user**, when I describe the setup I want in my own words, I want the builder to work out what capabilities that implies and ask clarifying questions so that I end up with the right requirements even if I didn't know the full list.*<br>• *As a **returning user**, when I point the builder at my current setup, I want it to analyze what's there and tell me what capabilities are present and missing so that I can upgrade rather than rebuild.* |
| PKG-25 | The builder agent MUST recommend a setup for the discovered needs, drawing on existing packages first, MAY propose structure the user did not explicitly name, and MUST identify the gaps that remain. | *As a **user**, when the builder knows what I need, I want it to recommend specific packages for each capability and tell me which capabilities have no existing package so that I see the full picture before committing.* |
| PKG-26 | The builder agent MUST be able to author a working package that provides a needed capability and satisfies that capability's contract. | *As a **user**, when the builder identifies a gap, I want it to offer to author a new package that satisfies the capability's contract so that the gap can be filled with a conforming package rather than a workaround.* |
| PKG-27 | The builder agent MUST be able to author a new capability type together with its conformance contract — extending the capability namespace, not only providing existing capabilities. | *As a **user**, when my setup needs something the kit doesn't have a capability type for yet, I want the builder to be able to define the new capability, write its contract, and author a provider for it so that the namespace grows with my needs.* |
| PKG-28 | The builder agent MUST be able to author reusable loop templates and actor templates — packages designed for independent composition and sharing — not only instantiate from existing ones. | *As a **user**, when I have a working loop I want to share, I want the builder to be able to package it as a reusable loop template that other teams can install and assign to their own agents so that good loops spread without copy-paste.* |
| PKG-29 | When part of a target cannot be expressed in the kit's terms, the builder agent MUST surface the resistance and record it as friction, rather than silently forcing a fit. | *As a **user**, when I describe a workflow that doesn't map to the kit's model, I want the builder to tell me what doesn't fit so that I know the limitation instead of getting a broken package.* |
| PKG-30 | When friction is recorded, the builder agent SHOULD propose a remediation and, when it does, MUST gate adoption on explicit user validation. | *As a **user**, when the builder proposes a way to address friction, I want it to wait for my approval before making changes so that I stay in control of how the kit evolves.* |
| PKG-31 | When the builder agent fails to author a package that passes verification, it MUST report the failure with the specific contract violations, rather than silently producing a non-conforming package. | *As a **user**, when the builder creates a package that fails verification, I want to see exactly which contract assertions failed and why so that I can decide whether to fix the package or adjust the contract.* |
| PKG-32 | The builder agent MUST be able to discover the kit's available capabilities, contracts, and packages — querying the catalogue and the structural model — and take newly available ones into its working repertoire without being re-shipped, so its recommendations and authoring stay current as the catalogue grows. | • *As a **user**, when capabilities and packages have been added to a catalogue since Smith shipped, I want Smith to be able to discover them and draw on them when it builds or advises so that I can benefit from the latest without waiting for a new Smith.*<br>• *As a **package author**, when I publish a new capability type to a catalogue, I want Smith to discover it by introspecting the kit rather than waiting for a new Smith, so that my package becomes usable the moment it lands.* |
## Assemble, Wire & Verify (9 features)

*Takes resolved packages and turns them into a running, verified setup connected to real infrastructure.*

| ID | Feature | User Story |
|---|---|---|
| PKG-33 | The system MUST compute a sufficient set of packages whose combined capabilities cover every requirement across the setup, avoiding unnecessary packages. | *As a **user**, when I declare what my setup needs, I want the system to figure out a set of packages that satisfies everything without pulling in more than necessary.* |
| PKG-34 | The system MUST support installing a blueprint as a unit — a curated starting point for a use case, installable in one step rather than package-by-package. | *As a **first-time user**, when I pick a blueprint, I want to install it in one step so that I don't have to select packages individually.* |
| PKG-35 | A package MUST be installable into a setup's workspace directory. | *As a **user**, I want to be able to install packages into my setup so that their capabilities become available.* |
| PKG-36 | The system MUST assemble a working setup from resolved packages within a workspace directory. | *As a **user**, when the system has resolved all dependencies, I want it to assemble everything into my workspace so that the setup is ready for wiring.* |
| PKG-37 | The system MUST be able to configure and connect a source to its concrete backing — prompting for the required connection values, validating credentials, and confirming the source is live before treating it as connected. This is distinct from installing the package that provides the source; when it happens depends on the family's authoring experience. | *As a **user**, when my setup includes a source that needs connecting, I want to be able to configure it — supplying the connection values, having credentials validated, and confirming it's live — so that the source is actually connected to real infrastructure, not just declared.* |
| PKG-38 | The kit MUST define a single base conformance contract that every setup must satisfy, covering contexts, loops, work items, actors, and sources. | *As a **user**, when I assemble a setup, I want the system to check the fundamentals — I have at least one context, loops defined, work items specified, actors assigned, sources connected — so that I don't end up with a structurally broken setup.* |
| PKG-39 | The kit MUST verify a candidate setup against every applicable contract (base + each capability type present), reporting pass/fail per contract, and MUST NOT mark a setup as ready until verification passes. | *As a **user**, when I finish assembling my setup, I want a clear pass/fail report per contract before anything goes live so that I never deploy a setup that doesn't meet its own standards.* |
| PKG-40 | The system MUST track which packages are installed in a setup and what capabilities they provide. | *As a **user**, I want to see an inventory of what's installed and what capability each package provides so that I know what my setup is made of.* |
| PKG-41 | Because a setup can run multiple coding agents at once, coding-agent support is a placement constraint, not a global install gate: the resolver MUST treat a package as installable as long as at least one coding agent present in the setup supports it, and MUST fail — surfacing the gap — only when no present coding agent does. | *As a **user** running a multi-agent setup, when I install a package only some of my agents support, I want it installed and later bound to a compatible agent rather than blocked; and when no agent in my setup supports a required package, I want the system to tell me exactly what's missing.* |

## Contexts, Sources & Connection Rules (5 features)

*These features govern how contexts relate to each other and to sources. A context is a domain of information and operations — your team, your project, your corporate directory, your Slack, your payslips system. A source is where a context's data comes from — a GitHub repo, a Jira board, a Slack workspace. An agent operates within and across contexts.*

| ID | Feature | User Story |
|---|---|---|
| CNTXT-01 | A user MUST be able to connect one context to another via a source and configure that connection's access — whatever permissions and controls the source provider offers. Access MUST be configurable independently of whether the source is part of the context: being in a context MUST NOT imply access, and having access MUST NOT imply being in the context. | • *As a **user**, when I connect one context to another through a source, I want to configure the connection's access — whatever permissions and controls the source supports — so that it grants exactly what I intend.*<br>• *As a **user**, I want a connection's access and the source's membership in a context to be independent knobs — changing one without the other — so that being in a context never implies access and having access never implies membership.* |
| CNTXT-02 | When an agent works in a connected source, its access MUST run on credentials that can be configured and bound to the connector or package that performs the work. Whether agents share an identity or each carries its own is a per-setup decision. | *As a **user**, when an agent needs to act in a connected source, I want to configure the credentials it uses and bind them to the connector that talks to the source — giving agents a shared identity or a unique one as my setup needs — so that access is authenticated the way I choose.* |
| CNTXT-03 | When a user connects multiple sources, the user MUST declare which context each belongs to, and sources declared into the same context MUST be treated as one unified context by agents. | • *As a **user**, when I connect a source, I want to choose which context it belongs to so that my sources are organized into the contexts I intend.*<br>• *As a **user**, when several sources belong to the same context, I want agents to treat them as one unified context so that working across them is seamless.* |
| CNTXT-04 | Each context MUST have exactly one designated home source, and no two contexts MAY share the same home source. | *As a **user**, when I set up multiple contexts, I want each to have its own home source and the system to prevent sharing so that context boundaries stay clean.* |
| CNTXT-05 | A context MAY draw on more than one source, each exposing type-specific operations. | *As a **user**, when a context needs more than one source, I want to connect several to it — each exposing its own type-specific operations — so that agents can work across all of them within that context.* |

## What a Conforming Setup Contains (11 features)

*These features define the structural rules that every conforming setup must satisfy — the "house spec."*

| ID | Feature | User Story |
|---|---|---|
| CONF-01 | A conforming setup MUST contain at least one agent and MAY contain more, each with independent configuration and behavior. | *As a **user**, I want to run as few or as many agents as my setup needs — a single agent or several side by side, each configured for its job — so that the setup matches the work.* |
| CONF-02 | A conforming setup MUST contain at least one loop and MAY contain more, each operating over a work tracker independently. | *As a **user**, I want to run as few or as many loops as my setup needs — one or several, each on its own cadence — so that the loops don't block each other.* |
| CONF-03 | A loop MUST be tracker-agnostic — it operates identically regardless of which tracker backs it. | *As a **user**, when I define a loop, I want it to work the same regardless of which tracker I choose so that switching trackers doesn't require redesigning my loop.* |
| CONF-04 | A conforming setup MUST include a workflow definition per loop — specifying its statuses, transitions, and gates. | *As a **user**, when I create a loop, I want to define its workflow with explicit statuses, transitions, and gates so that agents follow a predictable workflow.* |
| CONF-05 | A conforming setup MUST include per-agent configuration that governs the agent's behavior, skills, and persona within the setup. | *As a **user**, when I configure an agent for a role, I want to set its persona, skills, and behavioral rules so that the agent acts as I intend.* |
| CONF-06 | A conforming setup MAY include human-in-the-loop gates where progress pauses for operator input. | *As a **user**, when an agent finishes a phase, I want the loop to pause and wait for my approval before proceeding so that I stay in control of key decisions.* |
| CONF-07 | A conforming setup MUST route any communication between agents and human operators through the configured interface. | *As a **user**, when an agent reaches a step that requires my input, I want it to reach me through the configured channel and wait for my response so that we can collaborate asynchronously.* |
| CONF-08 | A loop step's actor MUST be assignable as either a human or an agent, and reassignable, with no behavioral distinction in how the loop addresses the actor. | *As a **user**, when I reassign a step from a human to an agent (or back), I want the loop definition unchanged so that human ↔ agent transitions are seamless.* |
| CONF-09 | A single actor MUST be able to participate in more than one context. | *As a **user**, when I have a shared agent, I want to assign it to more than one context so that it can provide cross-cutting guidance without duplicating the agent per context.* |
| CONF-10 | When an actor is assigned the steps it performs in a loop, the system MUST verify the actor is equipped for every step assigned to it — including that its coding agent supports the packages each such step uses — and MUST surface any gaps before the assignment takes effect. | *As a **user**, when I assign an agent to its steps in a loop, I want the system to tell me if the agent lacks a skill or runs a coding agent that doesn't support one of those steps' packages, so that I can equip it, switch its coding agent, or choose a different agent.* |
| CONF-11 | An agent template MUST declare the coding agent(s) it supports, and the concrete coding agent MUST be bound when the actor is instantiated. The kit's only hard runtime dependency is a running LLM — any supported coding agent can run an actor. | • *As a **user**, when I build a setup, I want to choose which coding agent(s) it runs on rather than being locked to one vendor, so that my agents and loops aren't tied to a single tool.*<br>• *As a **package author**, when I author an agent template, I want to declare the coding agent(s) it supports and have the concrete one bound at instantiation, so that the same template works across coding agents.* |

## Operate & Evolve a Running Setup (5 features)

*The setup is running. The user maintains it over time — swapping providers, adding capabilities, revisiting.*

| ID | Feature | User Story |
|---|---|---|
| PKG-42 | The system MUST support evolving a running setup — adding, removing, or replacing capabilities — re-verifying all contracts after each change and preserving unrelated configuration. When replacing a capability's provider, the system MUST NOT require re-running the full setup process. | • *As a **user**, when I decide to replace one capability's provider, I want to swap just that package, have the system re-verify everything, and keep my other configuration intact so that I evolve my setup without rebuilding it.*<br>• *As a **user**, when my team needs a new capability after standup, I want to add it and have all contracts re-checked so that the addition doesn't break what's already working.* |
| PKG-43 | A package MUST be removable from a setup. | *As a **user**, when I no longer need a capability, I want to remove its provider package so that my setup stays lean.* |
| PKG-44 | A package MUST be versioned, and a setup MUST support upgrading a package to a newer version and rolling back to an earlier one. | • *As a **user**, when a newer version of a package is available, I want to upgrade to it so that my setup picks up fixes and improvements.*<br>• *As a **user**, when a package update causes problems, I want to roll back to a previous version so that my setup returns to a known-good state.* |
| PKG-45 | The builder agent MUST support incremental operation — returning to a previously assembled setup to add, remove, or replace packages without starting over. | *As a **user**, when I want to evolve an existing setup, I want to re-run the builder and have it pick up where things are, find gaps, author new packages where needed, and re-verify so that I don't redo the entire setup.* |
| PKG-46 | A conforming setup MUST support installing new skill packages that provide additional capabilities to agents at runtime, without reconfiguring the agent from scratch. | *As a **user**, when a new skill package becomes available, I want to install it and have my agent gain that capability so that I can extend what agents can do without downtime or reconfiguration.* |

## Smith Gets Better at Serving You (3 features)

*Smith is trained and capable. Over time, it gets better at serving THIS user's specific needs — remembering what worked, what was customized, and why.*

| ID | Feature | User Story |
|---|---|---|
